# План реализации: DOCX → проверенный контекст для Copilot

## Назначение

Этот план развивает текущий Doc2Agent из детерминированного конвертера в
стабильный продуктовый конвейер для подготовки контекста GitHub Copilot и
других coding agents.

Целевая цепочка:

```text
неизменяемый исходный DOCX
  → детерминированное извлечение и структура
  → security gate
  → ограниченный LLM-патч
  → валидация
  → candidate
  → явное approval
  → approved knowledge.json
  → детерминированный Markdown для Copilot
```

`approved knowledge.json` — источник правды для пользователей системы.
Markdown — только воспроизводимое представление этого JSON для Copilot; он не
редактируется вручную и не становится альтернативным источником данных.

## Что уже есть

Текущая реализация уже покрывает основу безопасного конвейера:

- `Converter` создаёт raw Markdown, медиа и метаданные из DOC/DOCX/RTF;
- `MarkdownNormalizer` и `StructuralAnalyzer` детерминированно строят
  `document.json`;
- `DocumentValidator` и `SecurityGateway` формируют статус готовности;
- семантический слой изолирован за интерфейсом провайдера;
- `knowledge.json` не изменяет `document.json`, а хранит аннотации с
  `EvidenceRef`;
- есть offline fixture evaluation и явный adapter для реального LLM-провайдера;
- реализованы candidate, proof review, atomic approval, rollback и
  детерминированный Copilot Markdown;
- Web UI связывает upload, candidate, proof, approval и публикацию.

Не следует переписывать эти части ради новой архитектуры. Этапы 0–5 ниже
зафиксированы как реализованные границы. Следующий приоритет — этап 6:
измерить качество реального provider до оптимизации runtime.

## Неподвижные границы

1. `Converter` faithfully переносит источник и не делает семантических
   выводов.
2. `StructuralAnalyzer` остаётся детерминированным и не вызывает LLM.
3. LLM не может изменить исходный файл, raw Markdown, `document.json` или
   структурные блоки.
4. Каждый семантический факт обязан иметь проверяемое доказательство в
   исходной структурной версии.
5. Только approved-снимок может быть опубликован для Copilot.
6. Ошибочный, отклонённый или незавершённый запуск не меняет текущий
   approved-снимок.
7. При одинаковом approved-входе и конфигурации рендер Markdown должен
   создавать одинаковые байты.

## Артефакты и статусы

### Исходные и детерминированные артефакты

| Артефакт | Назначение | Создатель |
| --- | --- | --- |
| `source-manifest.json` | Идентичность исходного файла и его хеш | SourceRegistry |
| `raw/*.md`, `media/`, `metadata/` | Faithful-конвертация | Converter |
| `normalized/*.md` | Воспроизводимая нормализация | MarkdownNormalizer |
| `structured/*.document.json` | Каноническая структура | StructuralAnalyzer |
| `validation/*.validation.json` | Детерминированная проверка контракта | DocumentValidator |
| `security/*.security.json` | Решение security gate и безопасный вид | SecurityGateway |

### Семантические и публикуемые артефакты

| Артефакт | Назначение | Статус |
| --- | --- | --- |
| `artifacts/<source-version>/enrichment/*.enrichment-patch.json` | Ограниченный ответ LLM для конкретных блоков | промежуточный |
| `artifacts/<source-version>/candidate/*.knowledge.json` | Валидированный, но ещё не утверждённый снимок | candidate |
| `approval-log.jsonl` | Append-only запись решения человека | аудит |
| `approved/<document-key>/current.knowledge.json` | Последняя утверждённая каноническая версия конкретного логического документа (`document-key` безопасно выводится из document_id) | published |
| `copilot-context/<source-name>--<document-id>/INDEX.md` и `<source-name>.md` | Производный контекст для Copilot | generated |
| `copilot-context/manifest.json` | Хеши и список сгенерированных файлов | generated |

## Модель доказательства

Нужно постепенно заменить простую ссылку `source_ids` на явный
`EvidenceRef`:

```json
{
  "source_id": "sha256:...",
  "block_id": "block:...",
  "structural_sha256": "...",
  "support": "explicit"
}
```

Допустимые `support`:

- `explicit` — утверждение прямо сказано в блоке;
- `inferred` — допустимый, но не дословный вывод;
- `ambiguous` — данных недостаточно для надёжного утверждения.

Для первого продуктового релиза в Copilot публикуются только `explicit`
факты. `inferred` и `ambiguous` остаются видимыми ревьюеру, но требуют явной
политики публикации.

## Поэтапная реализация

### Этап 0 — контракты и воспроизводимость (реализовано)

**Цель:** зафиксировать идентичность артефактов до добавления новых runtime
возможностей.

- Ввести `SourceManifest`: SHA-256 исходных байтов, имя, размер, MIME,
  время приёма и версию схемы.
- Ввести canonical JSON serialization для хешируемых контрактов.
- Добавить `structural_sha256` в результат структурного анализа.
- Ввести `EvidenceRef` и миграционный режим, совместимый с текущими
  `source_ids`.
- Добавить тесты, что одинаковый вход даёт одинаковые IDs и хеши.

**Готово, когда:** любой semantic candidate можно однозначно связать с
конкретным исходным файлом и конкретной структурной ревизией.

### Этап 1 — безопасный приём DOCX (реализовано)

**Цель:** отклонять опасные или неподдерживаемые документы до Converter.

- Добавить DOCX preflight: сигнатура, ZIP-структура, повреждённый/запароленный
  пакет, архивные лимиты, опасные пути, макросы и внешние relationships.
- Явно классифицировать: `pass`, `requires_review`, `block`.
- Сохранять исходные байты неизменяемо по content hash.
- Ничего внешнего из relationships автоматически не загружать.
- Неподдерживаемое содержимое фиксировать в диагностике, а не терять молча.

**Решение о форматах:** DOCX становится безопасно поддержанным основным
форматом. Поддержку DOC/RTF не удалять без отдельного продуктового решения;
для них можно временно сохранить текущий путь с явно более ограниченной
гарантией preflight.

**Готово, когда:** опасный или повреждённый DOCX не доходит до Converter, а
повторная загрузка тех же байтов определяется как тот же источник.

### Принятое решение: хранение исходников и связь версий

Приложение хранит принятый оригинал и все его артефакты в файловом хранилище,
разделённом по `source_id` (content hash). Оно не меняет пользовательский
исходный файл и не использует RAG как хранилище.

Изменение DOCX создаёт новый `source_id` и новый набор артефактов; прежняя
версия не перезаписывается. Повторный приём неизменённых байтов должен
переиспользовать уже существующий источник.

Каталог версий связывает несколько `source_id` с одним стабильным логическим
идентификатором документа и хранит указатель на актуальную версию. Конкретное
хранилище каталога выбирается по нагрузке: сначала простой файловый индекс,
SQLite — при параллельных запусках, очереди или необходимости долговременного
управления состоянием.

Каждый `document.json` содержит `source_manifest` и `structural_sha256`.
Будущий candidate/approved `knowledge.json` обязан ссылаться на эти значения
через `EvidenceRef`, поэтому любой опубликованный факт можно проверить по
конкретной версии DOCX и конкретному content block.

История версий сохраняется по умолчанию, но не считается бессрочным архивом.
Удаление документа должно быть явным действием с проверкой целевого
логического документа: оно согласованно убирает его из активного каталога и
перемещает исходники, артефакты, approved-снимки, Copilot-контекст и относящиеся
к документу записи approval-журнала во внутреннюю корзину либо сообщает, почему
операция пока небезопасна. Автоматическое удаление старых версий без заданной
retention-политики запрещено. Необратимая очистка корзины требует отдельной
retention-политики.

### Этап 2 — ограниченный LLM-контракт (реализовано; quality gate впереди)

**Цель:** подключить LLM без передачи ему власти над канонической структурой.

- Ввести строгую Pydantic-модель `EnrichmentPatch`.
- Передавать LLM только `sanitized_document` после успешных validation и
  security gates.
- Разбивать документ на ограниченные section scopes; не отправлять весь
  большой документ одним запросом.
- В патче требовать `source_id`, `structural_sha256`, список разрешённых
  `block_id`, факты и доказательства.
- Запрещать неизвестные поля и факты без `EvidenceRef`.
- Сохранять полный prompt/response отдельно от production-логов либо не
  сохранять вовсе; в логах — только IDs, хеши, решение и диагностические коды.

**Готово, когда:** LLM может предложить только аннотации в пределах заданных
блоков и не способен вернуть замену `document.json`.

### Этап 3 — валидация semantic patch и candidate (реализовано)

**Цель:** превратить ответ модели в проверяемый кандидат, а не в публикацию.

Порядок проверок:

1. Схема patch.
2. Совпадение `source_id` и `structural_sha256`.
3. Принадлежность всех `block_id` разрешённому scope.
4. Наличие и корректность доказательств.
5. Уникальность локальных идентификаторов.
6. Доменные правила для `requirement`, `decision`, `action_item`.
7. Конфликты с уже известными facts в этом candidate.

После успешной проверки merger создаёт candidate `knowledge.json`. Никакой
провайдер и никакой LLM не пишут в `approved/` напрямую.

**Готово, когда:** невалидный или недостаточно обоснованный patch не создаёт
candidate, а валидный candidate имеет собственный content hash.

### Этап 4 — approval и публикация (реализовано)

**Цель:** отделить автоматическую обработку от решения о публикации.

- Добавить команду просмотра candidate и его проверочных отчётов.
- Approval связывать с точным candidate hash.
- Писать append-only запись: кто, когда, какой candidate и какое решение.
- Публиковать approved-снимок атомарно через временный файл и rename.
- Поддержать rollback на предыдущий approved snapshot.

**Готово, когда:** неудачный новый запуск, отклонённый candidate или падение
во время публикации не меняют `approved/<document-key>/current.knowledge.json`.

### Этап 5 — Markdown для Copilot (реализовано)

**Цель:** дать IDE компактный и достоверный контекст.

- Реализовать `TopicRenderer`, читающий только approved snapshot.
- Для каждого логического документа создавать отдельную папку
  `copilot-context/<source-name>--<document-id>/` с `INDEX.md` и Markdown,
  названным по исходному DOCX.
- Добавлять заголовок `GENERATED — DO NOT EDIT`, approved hash, source ID и
  дату публикации.
- Стабильно сортировать секции и факты.
- Создавать manifest со списком сгенерированных файлов и их хешами.
- Рендерить во временную директорию, валидировать manifest, затем атомарно
  заменять целевой каталог.

Тематическое разбиение на `modules/`, `apis/`, `flows/` и `decisions/`
добавляется только после появления реальной потребности и конфигурации тем.

**Готово, когда:** одинаковый approved JSON даёт байт-в-байт одинаковый
Markdown, а Copilot читает только generated-каталог.

### Этап 6 — качество, кеш и возобновление (следующий)

**Цель:** масштабировать уже работающий продуктовый путь.

- Расширить golden corpus DOCX: RTL, таблицы, списки, изображения, ссылки,
  комментарии, tracked changes и неподдерживаемые элементы.
- Добавить quality gate для реального LLM по размеченному набору.
- Вводить cache key из хешей входа, версии схемы, prompt/config/model версий.
- Добавить resume только после того, как стадии имеют явные входы, выходы и
  идемпотентность.
- SQLite/state-store и locking вводить при появлении параллельных запусков или
  необходимости долговременного управления заданиями.

**Первый slice:** собрать 5–10 DOCX с ожидаемыми фактами и proof, запускать
реальный provider на каждом и сохранять безопасные метрики missing,
unexpected и wrong-kind facts. До этого не добавлять cache, resume или фоновые
задачи.

## Что не входит в ближайший релиз

- graph database и граф отношений;
- vector RAG и retrieval-инфраструктура;
- OCR, SmartArt, charts и извлечение из изображений;
- автоматическое скачивание внешних ссылок;
- ручное редактирование generated Markdown;
- глобальный EntityResolver для междокументной идентичности;
- распределённая очередь задач.

Они не нужны, чтобы получить устойчивую цепочку «документ → проверенный
контекст Copilot», и не должны задерживать её.

## Минимальный набор CLI-команд

Названия окончательно фиксируются при реализации, но границы должны быть
такими:

```text
doc2agent ingest source.docx
doc2agent pipeline source.docx
doc2agent enrich <structural-artifact>
doc2agent validate-patch <patch>
doc2agent review <candidate-id>
doc2agent approve <candidate-id>
doc2agent publish
doc2agent render-copilot
doc2agent verify
```

Команда `pipeline` остаётся детерминированной до security gate. Вызов LLM,
approval и публикация — отдельные, наблюдаемые действия.

## Ближайшая реализационная задача

Начать с **Этапа 0** в отдельном небольшом изменении:

1. новые Pydantic-контракты `SourceManifest` и `EvidenceRef`;
2. вычисление хешей исходника и `document.json`;
3. тесты на стабильность хешей и связь evidence с конкретной структурной
   ревизией;
4. обновление существующей документации контрактов.

Этот этап не требует реального LLM, не меняет Converter и создаёт фундамент
для безопасного candidate/approved-потока.
